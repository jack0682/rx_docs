# 07. 설계 완료 후의 구현·검증·출시 계획

> 현재 구현 준비의 선행 순서는 [19 상세 설계 계획](19_detailed_design_sequence.md)이다. 이 문서의 G1 이후 구현 경로에도 [공통 작업 계약](contracts/v1.0/README.md)과 [셀 운영 계약](cell_operations/v1.0/README.md)의 필수 허가·gate·호환 규칙을 적용한다.

현재 작업 단계: **설계 문서 작성·구체화**. 실제 코드·빌드 기반·저장소 구축은 설계 정리 후 후속 지시에 따라 진행한다. 진행 순서는 [설계 로드맵](/Users/ojaehong/RX_automation/rx_ws/docs/00_design_roadmap.md)을 따른다.

[전체 문서 안내](/Users/ojaehong/RX_automation/rx_ws/README.md) · 구현과 인수 단계의 제안

## 1. 구축 순서의 원칙

이 장은 설계 로드맵을 정리한 뒤 진행할 구현·검증 계획이다. 현재는 계약·전이·모듈·화면·시험 사례를 문서로 구체화한다. 실행 가능한 모의 장비나 작은 프로토타입도 코드 구축에 해당하므로 후속 구현 단계에 둔다. 구현이 시작되면 선택한 첫 범위의 작은 실행 경로부터 실제 장비와 대조한다.

각 단계의 기간은 인원, 장비 접근, OEM 자료·변경 권한, 부품·설비 작업과 시험 가능 시간에 따라 산정한다. 현재 정보로 출시 날짜·필요 인원을 확정하지 않는다.

## 2. 단계별 산출물과 완료 기준

| 단계 | 만들거나 결정할 것 | 필수 산출물 | 완료 판단 |
|---|---|---|---|
| G0 문제·범위 | 첫 품목·사이클 범위, 로봇 선정 계획, 책임·개입·판정 기준 초안 | 요구사항, 장비 사실표, 작업·신호 목록, 위험·미결 목록 | 목표 사이클과 단계별 확인·결정 책임을 설명할 수 있음 |
| G1 계약·최소 경로 | 작업 하나의 의미와 앱→Runtime→모의 장비 | 스키마, 전이표, 모의 모듈, 화면·기록 | 정상·거부·불명·중복을 구분해 관측 가능 |
| G2 개별 실장비 | 선정 로봇과 Q03UDVCPU의 실제 접속·관측·작업 | 어댑터·프로파일·단위 시험 기록 | 실제 API·신호와 계약 의미가 일치 |
| G3 첫 셀 시연 | 기구·PLC·로봇·공정의 합의된 결합 | 공정 패키지, 초기 조건, 시연·이상 시험 기록 | 합의된 범위의 실제 소재 공급 수행 |
| G4 운영 파일럿 | 반복 운전·개입·복구·설치·진단 | 현장 측정, 결함 처리, 운영·복구 문서 | 인수 목표와 남은 제한을 판단할 자료 확보 |
| G5 첫 납품 | 검증 릴리스·설정·설치·교육·인수 | 납품 패키지, 시험·교육·지원 명세 | 인수 기준 충족과 지원 준비 확인 |
| G6 반복 납품 | 두 번째 장비·품목·현장 적용 | 변경·재사용·회귀·원가 기록 | 공통화 효과와 확장 비용을 실제로 확인 |

G0의 범위·자료 정리는 현재 설계 작업에서 다룬다. G1 이후의 코드 구축·실행 시험은 설계 정리와 후속 착수 지시 이후에 진행한다. 설계 중에는 현장 자료 확인과 계약·모델·상태·시험 명세 작성을 병행할 수 있다. G2의 물리 시험 전에는 해당 동작의 책임·관측·제어권·보호·개입 조건을 확보하고, G3에서는 셀 전체 결합 조건을 확정한다.

## 3. 처음 만드는 작은 실행 경로

첫 구현의 목표는 **화면에서 작업 하나를 요청하고, 같은 작업의 접수·진행·결과를 기록과 함께 확인하는 것**이다.

1. 작업의 범위·입력·완료 조건·중단·불명 처리를 한 장에 정의한다.
2. operation ID와 적용 프로파일·공정 버전을 포함하는 요청을 만든다.
3. Runtime이 중복·입력·능력·자원 조건을 확인하고 의도를 기록한다.
4. 모의 모듈이 접수·지연·완료·거부·응답 유실을 생성한다.
5. 같은 요청의 상태·근거·원본 오류를 앱과 저장소에서 확인한다.
6. Runtime을 재시작해 미결 작업을 불러오고 새 요청을 자동 재전송하지 않는지 확인한다.

이 단계에서 예쁜 화면 전체나 범용 편집기보다 판단과 상태가 사용자에게 정확히 전달되는 경로를 우선한다. 이후 모의 모듈 대신 실제 어댑터를 붙인다.

## 4. 첫 실장비 연결의 순서

### 4.1 Mitsubishi 레이저 PLC

확인된 Q03UDVCPU의 현재 프로젝트·통신 설정과 OEM 외부 인터페이스를 확보한다. 기존 Ethernet 사용 목적, 허용 접근, 신호 의미를 확인하고 읽기 관측부터 실제 상태와 대조한다. 그다음 합의된 작업 요청·접수·완료 경로를 검증한다.

기존 handshake가 있으면 적합성을 확인해 사용하고, 없으면 PLC 담당자와 필요한 요청·결과 영역과 논리를 설계한다. 사진의 배선·예시 도식·예비 슬롯을 완성된 연동 명세로 사용하지 않는다. [구체적인 조사 항목](/Users/ojaehong/RX_automation/rx_ws/references/laser_plc_interface.md)

### 4.2 선정 로봇

OMY·UR5e·FR3 중 첫 장비와 설치 버전을 선정한다. 연결·모드·교정·tool·gripper를 확인하고, 범위가 한정된 동작에서 접수·완료·중단 의미를 실제 관측과 비교한다. gripper 움직임과 소재 보유의 확인을 구분한다.

로봇별 어댑터를 한 번에 모두 완성하기보다 첫 경로를 실제로 끝낸 뒤 이질적인 두 번째 경로로 계약의 일반성을 검증한다. 두 번째 경로의 추가가 공통 코어 수정 없이 가능한지는 측정할 결과이며 선험적 보장은 아니다.

후속 요구에 따라 자사 지정 패키지 전체는 기본 의존·지원 범위에 포함한다. 위 순서는 첫 셀의 작업 검증 순서이며 다른 자사 제품군의 지원을 선택 기능으로 미루는 결정이 아니다. 각 제품군의 필수 기능·모델·환경에 대한 지원표와 검증을 별도로 완료해야 그 범위를 출시 지원으로 선언할 수 있다.

## 5. 검증 체계

| 시험 범위 | 핵심 사례 | 입증할 것 |
|---|---|---|
| 계약·코어 | 같은 ID 다른 입력, 접수/완료 구분, 불명·경합 | 장비 없이 공통 규칙의 일관성 |
| 모듈 적합성 | 미지원 기능, 원본 오류, 오래된 상태, 수명주기 | 선언과 구현의 일치 |
| 저장·재시작 | 기록 실패, 전송 전후 중단, 재시작, 중복 이벤트 | 의도·결과의 보존과 미결 조정 |
| 장비 단위 | 실제 모드·동작·오류·중단·연결 유실 | 제조사 기능과 작업 계약의 일치 |
| 셀 통합 | 소재·척·문·로봇·작업자, 초기 조건·잔류 상태 | 기계 간 전제·제어권·운영 흐름 |
| 배포·복원 | 새 PC 설치, 설정 복원, 버전 불일치, 용량 부족 | 다른 담당자의 재현 가능한 운영 |
| 사업 파일럿 | 노동 투입·개입·공급 대기·진단 공수 | 기대 가치와 실제 비용의 비교 |

제조사 시뮬레이터, 모의 장비, 실제 제어기, 실제 셀은 서로 다른 시험 범위를 가진다. 시뮬레이터의 기능·에디션·통신 제한을 확인하고, 모의 시험 통과를 실제 센서·정지·안전 기능 검증으로 확대하지 않는다.

## 6. 반드시 포함할 장애 시나리오

| 상황 | 기대 동작 |
|---|---|
| 요청 전달 후 결과 응답 유실 | unknown을 표시하고 의존 후속 작업 제한 |
| 명령 연결은 살아 있고 상태 스트림만 중단 | 이전 정상값을 최신 관측으로 인정하지 않음 |
| 장비 또는 RX가 재부팅 | 연결 세대·미결 요청·잔류 명령·물리 상태를 조정 |
| 반복 클릭·BT 반복 tick·중복 메시지 | 같은 논리 작업이 중복 물리 요청으로 늘지 않음 |
| 같은 ID로 다른 작업 입력 | 충돌 거부와 진단 기록 |
| 중단 중 완료 결과 도착 | 장비별 증거·순서 규칙으로 판단, 충돌 보존 |
| 저장소 오류·용량 부족 | 정해진 신규 요청 제한과 운영 경고, 기존 동작 별도 처리 |
| 펜던트·HMI에서 수동 조작 | 제어권·전제 무효화와 자동 복귀 절차 적용 |
| 구성·tool·firmware 불일치 | 적용 프로파일의 실행 범위 재평가 |
| 센서 모순·소재 보유 불명 | 후조건을 충족했다고 해석하지 않고 확인 경로 제공 |

실제 장비에 장애를 유발하는 시험의 방법·시점·범위는 장비·안전 담당자와 정한 계획을 따른다. 소프트웨어 시험 사례의 존재가 현장 시험 수행 허가를 뜻하지 않는다.

## 7. 시연·인수의 판정표

G0에서는 다음 항목의 정의·책임·미결 사항을 작성한다. G2의 개별 장비 기준은 해당 시험 전, G3 시연 기준은 시연 전, G4 파일럿의 측정·판정 목표는 파일럿 전, G5 납품 인수 기준은 계약·인수 시험 전에 각각 확정한다. 테스트 후 결과에 맞춰 성공 기준을 낮추는 방식으로 운영하지 않는다.

| 인수 항목 | 먼저 정할 값·범위 | 증거 |
|---|---|---|
| 작업 범위 | 품목·기준 수량·초기/종료 상태 | 공정 명세·실물 기록 |
| 반복성 | 반복 횟수·기간·허용 중단·실패 기준 | 모든 시도와 사유가 남은 실행 이력 |
| 시간 | 공급·교환·대기·복구 측정 구간과 목표 | 관측 시각·현장 측정 |
| 개입 | 정기 보충·확인·복구의 허용 범위 | 개입 사건·시간·주체 |
| 품질·소재 | 취급 완료와 검사 합격의 판정 주체 | 센서·검사·확인 기록 |
| 복구 | 시험할 단절·수동 조작·재시작 사례 | 복구 절차와 재개 근거 |
| 운영성 | 교육받은 다른 담당자의 수행 범위 | 설치·운전·진단 재현 시험 |

현재 목표 숫자는 미정이다. 이것은 시험 생략 사유가 아니라 파일럿·인수 전에 결정해야 할 개발 입력이다.

## 8. 작업 분할과 팀 병행

| 작업 묶음 | 독립적으로 진행할 일 | 합류 지점 |
|---|---|---|
| 현장·기구·전기 | 실제 책임·센서·배선·tool·안전 경계 | 작업 명세·프로파일 |
| 코어·저장 | 식별·상태·기록·재시작과 모의 시험 | 공통 계약 |
| 로봇 연동 | 선정 장비 API·모드·관측·중단 | 어댑터 적합성 |
| PLC 연동 | Q03 설정·기존 handshake·신호 검증 | 어댑터·PLC 프로파일 |
| 앱·공정 | 준비·진행·이상·복구 화면과 첫 공정 | 같은 요청·이벤트·버전 |
| 검증·배포 | 시험 명세·패키지·설치·진단 도구 | 검증 릴리스 |

현재는 공통 계약 초안을 기준으로 모듈 명세·화면 흐름·시험 시나리오의 설계를 병행한다. 모의 구현과 실제 코딩은 후속 단계에 둔다. 공통 명칭·상태·버전의 설계 변경은 관련 문서에서 함께 검토한다.

## 9. 설계 정리 후 구현 착수 순서

설계 기준판과 첫 셀 범위·담당·장비 자료를 재확인한다. 코드 착수 이후에는 정리된 작업 계약과 전이표에 따라 모의 경로를 구현하고, 실장비 검증 결과로 필요한 설계를 수정한다. 이후 소재 공급 시연과 운영 파일럿에서 인건비·개입·지원 공수를 측정한다.

기존 코드 재사용은 이 과정의 별도 기술 검토다. 동작 경험, 계약 적합성, 변경·회귀 비용을 평가해 채택하며, 이 문서가 전면 재작성이나 특정 저장소 폐기를 결정하지 않는다.
