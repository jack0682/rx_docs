# 08. 납품·업데이트·유지보수와 팀 운영

현재 작업 단계: **설계 문서 작성·구체화**. 실제 코드·빌드 기반·저장소 구축은 설계 정리 후 후속 지시에 따라 진행한다. 진행 순서는 [설계 로드맵](/Users/ojaehong/RX_automation/rx_ws/docs/00_design_roadmap.md)을 따른다.

[전체 문서 안내](/Users/ojaehong/RX_automation/rx_ws/README.md) · 납품·지원 운영 모델 제안

## 1. 고객에게 넘기는 납품 단위

납품 단위는 실행 파일뿐 아니라 **검증된 소프트웨어 조합·현장 패키지·운영 절차·인수와 지원 범위**다. 기구·전기 설계와 실제 장비 revision도 이 조합에 연결한다.

| 납품물 | 포함할 내용 |
|---|---|
| 소프트웨어 배포 명세 | Runtime·앱·어댑터·의존성·OS·CPU 버전, 해시 |
| 현장 패키지 | 장비·품목·공정·tool·교정·지그·신호 매핑·정책 버전 |
| 장비 측 구성 | PLC·로봇 프로그램과 설정의 참조·백업·변경 이력 |
| 검증 기록 | 계약·모의·실장비·셀·복원 시험과 적용 범위 |
| 보호 기능의 책임·검증 참조 | 설비에서 요구하는 보호 기능의 담당·적용 범위와 적합한 책임자가 확인한 검증 결과 |
| 운영 문서 | 초기 준비·소재 보충·운전·중단·개입·복귀 절차 |
| 지원 자료 | 진단 수집·연락·에스컬레이션·지원 버전과 제외 범위 |
| 상업·자산 명세 | 장비·소프트웨어 사용 조건, 보증·변경·교육·인수 범위 |

기록에는 비밀값을 직접 포함하지 않는다. 현장 주소·프로그램·사진·로그의 접근·반출 범위는 고객·회사 운영 조건에 맞춰 관리한다.

## 2. 설치에서 인수까지

| 순서 | 확인·수행할 일 | 남길 기록 |
|---|---|---|
| 출하 전 | 설치 대상 조합·필수 의존성·설정·시험 확인 | 릴리스 명세·검증 결과 |
| 현장 설치 | PC·장비 식별·통신·계정·시간·저장·자동 시작 구성 | 설치 기록과 실제 버전 |
| 시운전 | tool·교정·신호·제어권·동작·중단·복구 대조 | 현장 프로파일과 시험 증거 |
| 교육 | 작업자·유지보수 역할별 정상·이상 절차 수행 | 교육 대상·범위·확인 결과 |
| 인수 | 합의한 품목·반복·시간·개입·복구·운영 기준 평가 | 인수 결과·예외·후속 조치 |
| 지원 전환 | 담당자·진단 수집·보증·변경 절차 인계 | 지원 시작 기준과 연락 체계 |

인수에는 현재 구현한 범위와 제한을 명시한다. 남은 결함이 있는 경우 영향·임시 운영 조건·해결 책임을 합의하며 이를 숨긴 채 지원 완료로 표시하지 않는다. 필수 보호 조건이 충족되지 않은 운전을 예외 합의로 허용하는 의미는 아니다. 해당 운전 범위를 제한하고 필요한 검증을 마친 뒤 인수한다.

## 3. 진단 패키지

지원 담당자는 같은 현장에 접속하지 않아도 가능한 범위에서 사건을 재구성할 수 있어야 한다. 다음 정보를 작업 ID와 발생 구간으로 모은다.

- 제품·어댑터·장비 firmware·PLC/로봇 프로그램·현장 패키지 버전.
- 작업지시·공정 실행·장비 작업·전달 시도와 연결 세대.
- 접수·관측·판정·오류·제어권·개입의 순서와 원본 코드.
- 상태 품질·수신 시각·시계 상태와 로그 손실·저장 오류.
- 수행한 복구 조치와 현재 제한·미결 작업.

관절·센서 전체 데이터를 무제한 저장하지 않는다. 작업 판단 근거, 짧은 진단 구간, 집계 데이터를 분리하고 보존 기간·용량·반출 권한을 정한다. 진단 자료가 없거나 일부 유실된 경우 그 자체를 표시한다.

## 4. 장애 대응의 역할

| 단계 | 담당 역할 | 수행할 일 |
|---|---|---|
| 현장 1차 | 교육받은 작업자·유지보수 담당 | 허용된 확인·중단·복구 절차, 상태·증거 보존 |
| 제품 지원 | RX 지원 담당 | 버전·로그·작업 이력 대조, 공통/연동/현장 원인 분류 |
| 전문 대응 | 코어·어댑터·기구·전기·OEM 담당 | 원인 수정과 필요한 시험·현장 조치 |
| 변경 배포 | 릴리스·현장 책임자 | 영향·지원 조합·복원·인수 재평가 |

실제 담당 인원·연락처·대응 시간은 계약과 팀 편성으로 정한다. 소프트웨어가 복구 버튼을 제공한다는 이유로 현장 담당자의 작업 범위가 자동 확대되지는 않는다.

## 5. 업데이트와 롤백

| 단계 | 요구 |
|---|---|
| 변경 평가 | 영향받는 계약·프로파일·데이터·장비·안전 경계 확인 |
| 사전 준비 | 미결 작업 처리·운영 중단 조건, 구성·데이터·장비 설정 백업 |
| 설치 | 지원 조합 확인, 필요한 마이그레이션·서비스 교체 |
| 재확인 | 실제 장비 상태·버전·제어권·신호·작업 재검증 |
| 복귀 | 인수 범위의 운영 재개와 변경 기록 |
| 롤백 판단 | 이전 바이너리뿐 아니라 데이터·설정·장비 프로그램 호환성 확인 |

업데이트 전에 백업했다는 사실만으로 어느 시점으로든 안전하게 되돌아갈 수 있는 것은 아니다. 새 버전에서 이미 물리 작업이 수행됐다면 과거 데이터 복원은 현재 소재·장비 상태와 충돌할 수 있다. 복원 후에도 현재 상태와 미결 요청을 다시 조정해야 한다.

원격 자동 업데이트는 첫 제품의 필수 기능으로 두지 않는다. 현장 운전과 호환성·복구 절차가 확보된 범위에서 관리된 업데이트부터 제공한다.

## 6. 지원 조합과 종료 정책

릴리스마다 지원 OS·CPU·Runtime·어댑터·SDK/ROS·firmware·프로파일 조합을 명시한다. 필수 실행 조건·관측 근거가 충족되지 않는 조합에서는 관련 물리 실행을 제한한다. 조회·진단처럼 실행을 유발하지 않는 기능의 제한도 구분해 알린다. 지원 종료 예고·장기 유지·부품 교체·업그레이드 조건은 계약과 제품 정책으로 정한다.

브라우저 UI 접속, 모의 시험, 장비 단위 검증, 셀 납품 검증을 구별해 표기한다. 한 단계의 성공을 전체 조합의 지원으로 확대하지 않는다.

## 7. 공통 제품과 현장 변경의 관리

| 변경 | 기본 소유 | 처리 방향 |
|---|---|---|
| 작업 식별·기록·공통 복구 결함 | 코어·제품 담당 | 공통 수정과 영향 조합 회귀 |
| 특정 SDK·통신 결함 | 연동 담당 | 어댑터 수정·버전·적합성 시험 |
| 배선·센서·기구·교정 변경 | 현장·기구·전기 담당 | 프로파일·설계 revision과 실물 재검증 |
| 품목·공정 순서 변경 | 공정 담당 | 새 공정 패키지·작업 조건·인수 영향 |
| UI·진단 개선 | 앱·지원 담당 | 사용자 흐름과 기존 API 호환성 검증 |

현장마다 코어를 별도 fork해서 운영하기보다 공통 릴리스와 현장 패키지를 유지하는 것을 기본으로 한다. 불가피한 현장 패치는 사유·소유자·시험·공통 반영 또는 종료 계획을 남긴다.

## 8. 팀의 계약과 책임

제품 책임자는 범위·우선순위·고객 가치와 지원 약속을 관리한다. 공정·기구·전기 책임자는 실제 작업·보호·관측의 의미를 제공한다. 소프트웨어 팀은 그 의미를 계약·실행·연동·앱으로 구현하며, 검증 담당은 범위와 증거를 대조한다.

장비 어댑터를 맡는 사람에게 줄 최소 자료는 작업 계약, 실제 인터페이스·프로파일, 모의 참조 모듈과 적합성 시험이다. 앱 담당자에게는 같은 상태·오류·개입 모델을 제공한다. 코드 인터페이스만 공유하고 완료·복구 의미를 각자가 추정하지 않게 한다.

## 9. 납품 종료와 철수

설비 교체·계약 종료 시 유지할 데이터, 넘길 설정·프로그램, 제거할 계정·접속 권한, 지원 종료 범위를 정한다. RX 서비스를 제거해도 남는 PLC·로봇 프로그램과 출력 상태, 기계 운전 절차를 현장 책임자와 확인한다. 소프트웨어 삭제를 물리 셀의 초기화나 안전한 원상복구와 동일시하지 않는다.
