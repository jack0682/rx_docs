## 1. 적용 범위와 상태

현재 계약 초안의 필드·메서드·상태 명칭은 검토용이다. [계약·프로토콜 설계 계획](15_contract_protocol_design_plan.md)에 따라 제공 보장·대안·대표 사례를 먼저 검토하고, 실제 메시지·전송 규약은 그 뒤 구체화한다.

이 문서는 OMY·UR5e·FAIRINO FR3, FANUC CNC/PMC, Siemens SINUMERIK/PLC 및 후속 확인된 첫 레이저 Mitsubishi PLC 조사에 근거한 **소프트웨어 설계 제안**이다. 실제 장비 지원 완료나 실행 가능한 현장 절차를 선언하지 않는다. 제조사 사실·버전·출처는 [인터페이스 연구보고서](/Users/ojaehong/research_RX/RX_first_cell_interface_research_v1.0.md)에 있다.

첫 셀은 네모엔지니어링 레이저열처리 설비의 소재 공급이다. 후속 사진에서 설비 PLC **Mitsubishi MELSEC-Q Q03UDVCPU**, CC-Link 모듈 **QJ61BT11N**과 아날로그 모듈이 확인됐다. PLC의 설치 버전·통신 설정·문·척·완료 신호와 레이저 가공 제어부의 관계, 첫 투입 로봇, 작업자 복구 범위는 미확정이다. 공통 설계는 진행할 수 있지만 이 빈칸을 채우기 전에는 현장 실행 프로파일을 승인할 수 없다. [PLC 연동 보완 기록](/Users/ojaehong/RX_automation/rx_ws/references/laser_plc_interface.md)을 함께 적용한다.

메인 PC는 공정과 장비 작업을 관장하고, 저수준 SDK·통신·신호는 연동 모듈이 처리한다. 외부 미니컴퓨터는 PLC와 같은 부속 제어장치다. RX를 실행하는 원격 worker를 전제하지 않는다.

## 2. 책임 분담

| 영역 | 맡는 책임 | 제공할 결과 |
|---|---|---|
| 구성·시운전 | 장비·신호·tool·지그·좌표계 등록, 검증 조합과 공정 패키지 확정 | 버전이 고정된 셀 구성과 검증 기록 |
| 공정관리 | 품목·수량·공정 버전과 작업 지시, 진행·실적 연결 | 작업 지시와 실행 이력 |
| 공정 실행기 | 순서·분기·동시 작업 계획, 공정별 조건과 복구 흐름 | 공통 계약에 따른 작업 요청 |
| 공통 Runtime | 요청 식별·중복 처리, 공통 실행 조건·자원 정책, 결과·기록·재시작 조정 | 일관된 작업 상태와 판단 근거 |
| 장비 연동 모듈 | SDK·프로토콜 호출, 원본 오류·상태 수집, 프로파일에 따른 의미 변환 | 접수·관측·결과 및 미지원 범위 |
| 기계 연동 프로파일 | 실제 모델·버전·옵션·신호와 작업 의미의 연결 | 이 기계에서 지원·검증한 작업 계약 |
| 장비 제어기·PLC | 국소 동작과 순차 제어, 장비 운전 조건·보호 기능 | 장비 측 접수·실행·상태·결과 |
| 운영 화면·작업자 절차 | 권한에 따른 시작·중단 요청, 상태·이상·개입 안내 | 개입 주체·시각·확인 내용과 재개 요청 |

표는 책임의 구분이며 프로세스·저장소 수를 확정하지 않는다. 공정 실행기는 BT나 상태기계 등을 사용할 수 있지만 공통 작업의 접수·완료 의미를 별도로 바꿀 수 없다. 현장 안전 기능은 위험성 평가에 따라 장비 제어기·안전 PLC·안전회로 등 적합한 경로에 배정하고, 일반 RX Runtime의 실행 허가와 구별한다.

## 3. 장비·프로파일 계약

### 3.1 기계 프로파일의 필수 내용

| 항목 | 내용 |
|---|---|
| 식별 | `device_id`, 기계 제작사·모델·일련번호, 제어기 제품군 |
| 버전 | firmware/Operate/PolyScope/WebAPP, SDK·ROS·컨트롤러, 어댑터·프로파일·계약 버전 |
| 접속 | endpoint·포트·serial·node/action, 인증·옵션 요구, 설정 파일 참조 |
| 제어권 | RX·PLC·펜던트·다른 PC 중 명령 가능한 주체, 모드 변경·수동 조작 감지 |
| 기능 | 작업별 지원 여부, 입력·결과 형식, 시작·완료·중단 조건 |
| 관측 | 원본 신호·자료형·단위·좌표계·품질·갱신 의미·요청 연관성 |
| 복구 | 단절·장비 재부팅·RX 재시작 때 조회·중복 억제·재개 가능 범위 |
| 검증 | 검증 대상 조합, 시험 항목·결과, 설정 해시, 승인 범위와 제한 |

인증 비밀은 프로파일 원문이나 진단 로그에 넣지 않고 비밀 저장 위치를 참조한다. 런타임에 검색된 capability는 설치 상태를 보여주는 자료이고, 납품 시 검증된 capability와 일치하는지 별도로 확인한다.

### 3.2 기능 선언

한 장비 전체에 `supports_completion=true` 하나를 붙이지 않는다. 같은 장비라도 관절 이동, 소재 집기, 프로그램 시작의 완료 근거가 다르다.

| 기능별 선언 | 선택지 또는 의미 |
|---|---|
| availability | `supported / unsupported / unverified` |
| request_schema, result_schema | 작업별 형식과 버전 |
| acceptance | 장비가 접수를 직접 확인하는지, 추론만 가능한지, 관측 불가능한지 |
| completion | 직접 결과 / 후조건 관측 / 권한 있는 사람 확인 / 관측 불가 |
| correlation | 장비 요청 ID / 세션 내 handshake / 배타 실행과 전후 관측 / 연관 불가 |
| stop | 지원 요청 종류·범위와 정지 확인 조건 |
| resume | 이어서 실행 / 처음부터 실행 / 별도 복구 절차 / 미지원·미확인 |
| replay_protection | 장비 측 중복 억제 범위와 보존 기간·재부팅 후 유지 여부 |
| reconciliation | 이전 결과 조회·현재 상태 대조·사람 확인의 가능 범위 |

지원 수준이 낮은 장비도 연결할 수 있다. 다만 자동 완료·자동 복구 범위를 그 수준에 맞춰 제한한다. `unverified`를 `unsupported`로 단정하거나, `supported`로 올려서 배포하지 않는다.

## 4. 작업 요청과 식별

작업 요청은 다음 정보를 가진다. 아래 이름은 언어·통신 방식에 독립적인 개념 스키마이며 실제 함수 시그니처는 후속 설계에서 정한다.

| 필드 | 의미 |
|---|---|
| `operation_id` | RX에서 하나의 논리적 작업을 식별. 다른 요청 내용에 재사용하지 않음 |
| `intent_digest` | 대상·작업·의미 있는 입력·적용 버전의 동일성 확인 값 |
| `operation_type`, `schema_version` | 예: `robot.execute_motion@1`, `fixture.set_clamp@1` |
| `target_device`, `profile_version` | 실행할 장비와 검증 프로파일 |
| `process_run_id`, `step_id` | 어느 공정 실행·단계에 속하는지 |
| `parameters` | 작업별 스키마로 검증한 입력. 단위·좌표계·tool·program 버전 명시 |
| `requested_by` | 사용자 또는 시스템 주체와 권한 |
| `resource_requirements` | 로봇·척·공유 공간 등 필요한 배타 사용 조건 |
| `timing_policy` | 접수 대기, 진행 감시, 결과 확인의 시간 정책 참조 |

`intent_digest`를 만들 입력의 정규화·단위·기본값·부동소수 표현 규칙도 버전으로 정해야 한다. 같은 ID·같은 의미의 재요청은 기존 작업 상태를 반환하고, 같은 ID·다른 의미는 충돌로 거부한다.

작업이 ‘목표 상태를 충족시키기’인지 ‘새 물리 동작을 반드시 수행하기’인지도 명세에 넣는다. 이미 닫힌 척을 확인해 성공할 수 있는 작업과, 이번 요청으로 새 고정 사이클을 수행해야 하는 작업은 완료 근거가 다르다.

장비에 보내는 각 전달 시도에는 별도 `attempt_id`를 둔다. 장비 요청 번호가 있으면 `native_request_id`로 연결한다. 이 세 식별자를 하나로 취급하지 않는다. API 호출의 자동 재시도는 작업 의미와 장비의 중복 방지 능력이 확인된 경우에만 허용한다.

## 5. 접수·활동·결과의 분리

### 5.1 접수 단계

| 상태 | 의미 |
|---|---|
| RX 기록 완료 | RX가 요청을 저장함. 장비 접수를 의미하지 않음 |
| 전달 시도 | 연동 모듈이 전달을 시도함. 실행 여부는 별도 |
| 장비 접수 확인 | 이번 요청을 장비가 수락했다는 근거가 있음 |
| 거부 확인 | 이번 요청이 실행 대상으로 받아들여지지 않았다는 근거가 있음 |
| 접수 불명 | 전달·접수 여부를 확인할 수 없음 |

### 5.2 현재 활동과 작업 결론

현재 활동은 `idle / executing / paused / stop_observed / unknown`처럼 표현할 수 있다. 작업 결론은 `pending / succeeded / failed / cancelled / rejected / unknown`으로 별도 관리한다. 각 값은 관측·정의된 판정 규칙에 따라 갱신한다.

특히 다음 규칙을 적용한다.

- `pending`: 아직 결론을 판정할 시점·조건에 도달하지 않았고, 선언된 관측·대기 범위 안에 있다. 필요한 접수·상태를 잃거나 결과 확인 기한을 넘겨 결론을 판정할 수 없게 되면 `unknown`으로 전환한다. 기한 초과 자체가 물리 실패의 증거는 아니다.
- `succeeded`: 이번 요청에 연결된 모든 필수 완료 조건과 근거가 확보됐다.
- `failed`: 이번 요청이 정의된 실패 조건에 도달했다. 부분 동작·잔류 상태는 별도 보존한다.
- `cancelled`: 요청된 중단의 정의된 범위가 확인됐다. 소재·척·위치가 초기 상태라는 뜻은 아니다.
- `rejected`: 실행 대상으로 수락되지 않았음이 확인됐다. 단순 타임아웃에 사용하지 않는다.
- `unknown`: 현재 증거로 이번 작업의 결론을 확정할 수 없다. 장비 활동 상태와 독립적이다.

`unknown` 이후 새로운 장비 결과나 검증된 재조정 근거가 들어오면 결론을 확정할 수 있다. 이전 기록은 지우지 않고 새 근거와 판정 변경을 연결한다. 폴링이 계속 `executing`을 보여준다는 이유로 불명이 해결된 것으로 처리하지 않는다. 반대로 현재 idle이라는 이유로 이전 작업을 성공으로 처리하지 않는다.

성공·실패·중단 등의 결론이 생겨도 자원은 자동으로 모두 해제하지 않는다. 로봇이 기계 내부에 있거나 소재의 보유 상태가 불명이라면 다음 동작에 필요한 해제 조건을 별도로 충족해야 한다.

## 6. 관측과 완료 근거

### 6.1 관측 봉투

| 필드 | 의미 |
|---|---|
| `observation_id`, `device_id` | 관측과 출처 식별 |
| `signal`, `value`, `unit`, `frame` | 무엇을 측정·보고했는지 |
| `quality`, `native_status` | `valid / uncertain / invalid / unavailable` 및 원본 품질·오류 |
| `received_at`, `received_monotonic` | RX가 받은 시각. 로컬 지연 판단에는 단조 시계 사용 |
| `source_timestamp`, `timestamp_semantics` | 장치 시각과 그 의미. 없는 값은 만들어 넣지 않음 |
| `source_sequence`, `connection_epoch` | 원본 순번과 RX 연결 세대. 순환·재부팅 규칙 포함 |
| `operation_ref`, `correlation_basis` | 어떤 요청과 관련되는지, 그 판단의 근거 |
| `profile_version` | 값과 판정 의미를 해석한 프로파일 |

수치 confidence 하나로 센서 품질·신선도·요청 연관성을 대체하지 않는다. 확률을 제공하지 않는 장비에 임의의 `confidence=1.0`을 넣지도 않는다.

유효성은 해당 신호의 갱신 계약으로 판단한다. 주기 스트림은 수신 지연과 누락을, change-only 신호는 품질·연결 생존·서버 갱신 의미를 함께 본다. 장치의 오래된 SourceTimestamp만으로 무효 처리하거나, 새로 읽은 캐시라는 이유로 무조건 유효 처리하지 않는다.

### 6.2 서로 다른 완료를 구분하는 예

| 확인된 사실 | 직접 결론 낼 수 있는 범위 | 추가 근거가 필요한 결론 |
|---|---|---|
| DYNAMIXEL 송신 성공 | 송신 단계의 통신 결과 | 관절 도달·소재 집기 |
| OMY trajectory action 성공 | 해당 controller 설정의 trajectory 결과 | 그리퍼 소재 보유·기계 접근 허가 |
| UR 프로그램 시작 응답 | 프로그램 시작 접수·응답 범위 | 이번 소재 공급 완료 |
| FR3 motion_done 값 | 유효한 상태라면 장비 운동 완료 표시 | 새 요청의 완료인지와 소재 상태 |
| SINUMERIK Select 성공 | 프로그램 선택 성공 | NC 시작·가공 완료 |
| PLC 출력·register 쓰기 응답 | 해당 명령/쓰기 처리 범위 | 문 닫힘·잠금·척 고정 |

제조사별 정확한 적용 범위와 출처는 연구보고서 §4–8에 있다. 완료 조건은 첫 현장의 실제 센서와 제어 논리를 확인해 채워야 한다.

## 7. 중단·재접속·재시작 계약

`request_stop(operation_id, stop_kind)`는 중단 요청이다. 응답은 요청 수락 여부와 지원 범위를 나타내며 실제 정지 완료는 별도 근거로 확인한다. `pause`, 일반 동작 종료, 안전 정지는 동일한 enum으로 뭉뚱그리지 않는다.

연결이 끊기면 RX는 관련 관측을 불명·이용 불가로 바꾸고, 그 관측에 의존하는 새 요청의 허가를 제한한다. 장비 측 단절 동작은 장비에 사전 설정·검증된 기능이 담당한다. RX가 끊긴 통신을 통해 이 동작을 보장하는 것은 아니다. RX가 중단 명령을 보내려 했다는 기록만으로 정지됐다고 표시하지 않는다. 안전 정지 기능의 책임과 일반 통신 중단 대응은 설비 설계에서 명확히 분담한다.

재접속·RX 재시작 후에는 다음 순서로 조정한다.

1. 저장된 미결 작업·적용 프로파일·이전 전달 시도를 읽는다.
2. 현재 장비·firmware·운전 모드·제어권과 연결 세대를 확인한다.
3. 장비가 결과를 보존한다면 요청 번호로 조회한다. 보존하지 않으면 현재 상태와 과거 기록만으로 어떤 결론이 가능한지 제한한다.
4. 이미 실행됐을 가능성이 있는 요청을 자동으로 다시 보내지 않는다. 재요청 조건이 명시된 작업만 별도로 판단한다.
5. 이전 명령의 큐 잔류·지연 실행 가능성을 조회·확인된 취소·제어권 격리 등 해당 장비에서 검증된 수단으로 처리한다. 현재 정지만으로 처리됐다고 판단하지 않는다. 확인할 수 없으면 관련 자원과 후속 동작의 제한을 유지한다.
6. 확정할 수 없는 소재·위치·척 상태는 정의된 현장 확인·복구 절차로 넘긴다.
7. 미결 명령과 실제 상태를 포함한 다음 작업 조건이 확보됐을 때 재개한다. 작업자 확인은 확인 범위와 근거를 기록하고 과거 자동 완료 증거를 소급 생성하지 않는다.

중단 요청과 완료 결과가 경합할 때는 메시지 도착 순서만으로 결론을 정하지 않는다. 이번 작업의 완료가 입증되면 중단 요청 이력을 보존하면서 성공으로 판정할 수 있고, 정의된 취소 완료가 입증되면 취소로 판정한다. 두 근거가 충돌하거나 순서를 판별할 수 없으면 불명으로 조정한다. 첫 작업의 전이표에 늦은 결과·중복 통지·중단 경합 사례를 포함해야 한다.

RX 내부 저장의 일관성과 물리 실행의 원자성은 다르다. 전송 직전·직후 중단 구간은 장비 handshake 없이는 없앨 수 없다. 따라서 최소 구현에서도 이 구간을 시험하고, 결과 불명을 관리하는 경로를 포함한다.

## 9. 설계 정리 후의 첫 개발 범위

첫 개발물은 다음 네 가지로 제한한다.

1. **버전 있는 작업 계약 한 종류:** 입력, 접수, 관측, 결과, 중단·불명 상태를 명시하고 접수·활동·결론의 전이표와 중단·완료 경합 사례를 작성한다.
2. **공통 실행 경로:** 작은 호출 화면 → Runtime → 모의 모듈 → 기록·결과 표시를 연결한다.
3. **실제 장비 프로파일과 어댑터 하나:** 설치된 모델·버전·관측 경로를 채운다.
4. **장애·재시작 시험:** 정상뿐 아니라 접수 거부, 응답 유실, 상태 지연, 중복 요청, 재시작과 개입을 검증한다.

모의 시험은 계약과 소프트웨어 상태 처리를 검증한다. 실제 장비 시험은 명령·관측·중단 의미를, 셀 시험은 소재·지그·문·척·작업자 절차의 결합을 검증한다. 시험 결과마다 대상 버전과 검증 환경을 기록한다.

프로파일 상태는 `draft → software_verified → hardware_verified → cell_validated`처럼 검증 범위를 표현할 수 있다. 이 상태 이름은 제안이며 각 승격은 필수 시험과 실제 적용 범위를 충족해야 한다. 전체 테스트 통과 수만으로 실물·셀 검증을 대체하지 않는다. 변경이 생기면 영향받는 검증 결과를 재평가한다.

공통 인터페이스를 설계하는 것은 맞지만, 함수 이름부터 확정하기보다 **실제 작업의 책임·입력·관측·결론을 먼저 정하고 이를 인터페이스로 표현한다.** 이 순서가 장비 추가 때 유지할 부분과 현장마다 바꿀 부분을 구분하는 기준이다.
