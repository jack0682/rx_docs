# RX 계약·프로토콜 설계를 위한 설계 계획 v0.1

> 2026-09-10 현재 계약의 규범 기준은 [RX 계약·프로토콜 v1.0](contracts/v1.0/README.md)이다. 이 문서의 선행 제안·예시는 v1.0과 충돌하면 대체된다. 자사 기본 지원 의무·두 이미지 경계는 유지하며, 실제 구현·실물 검증은 별도다.

## 1. 이번 단계의 목표

**계약과 프로토콜을 바로 확정하지 않고, 설계할 대상·순서·대표 사례·결정 기준·검토 산출물을 먼저 정한다.** 결과물은 구현 코드나 완성된 API가 아니라, 다음 설계 작업에서 같은 질문과 근거로 대안을 비교할 수 있는 작업 체계다.

이번 단계에서는 `.proto`, Rust/C++ 인터페이스 소스, Dockerfile, 실행 모의 프로그램을 만들지 않는다. 문서의 상태표·시퀀스·요청 예시·종이 위 사건 추적으로 설계를 진행한다. 기존 06·10·11 문서의 필드·메서드·상태 이름도 검토의 출발안이며 공개 계약으로 동결된 것은 아니다.

산출물은 이 계획, [결정·작업 목록](contracts/00_design_backlog.md), [시나리오 검토집](contracts/01_scenario_workbook.md)이다. 이 계획은 전체 로드맵의 S4–S7을 구체화한다.

## 2. 유지할 전제와 열어둘 결정

| 유지할 작업 전제 | 아직 검토할 결정 |
|---|---|
| 코어 언어 Rust | 실제 타입·필드·메서드·에러 코드 |
| RX 두 레포가 각각 컨테이너를 가짐 | 세션·연결·시작·종료의 정확한 교환 규칙 |
| platform은 ROS 비의존 코어·Runtime·공통 기록 | 요청 ID 생성 주체·범위·보존·정규화 방식 |
| solutions에 ROS·자사 필수 스택·실행기·Adapter·UI | 작업 종류와 상태·결과·중단의 상세 모델 |
| 자사 기본 지원표와 이미지 명세를 설계 입력으로 사용 | 능력 부족·관측 불명·수동 개입의 계약 |
| 설계 정리 후 코드 구축 | gRPC/Protobuf·HTTP/SSE의 최종 적용과 버전 |

Rust나 레포 수를 매번 다시 선택하지 않는다. 반면 현재 기술 후보가 특정 업무 의미를 자동으로 결정하도록 두지 않는다. 근거가 부족한 사항은 담당·영향·확인 방법을 가진 미결 결정으로 관리한다.

## 3. 설계할 층을 구분한다

| 층 | 답할 질문 | 문서 결과 |
|---|---|---|
| 작업 의미·책임 | 무엇을 요청하고 누가 어떤 사실·판정을 책임지는가? | 용어·책임·제공 보장·제약 |
| 논리 계약 | 입력·접수·관측·결과·실패·중단·재시작은 무엇을 뜻하는가? | 계약 카드·상태 전이·사례 |
| RX 애플리케이션 프로토콜 | 누가 언제 무엇을 보내고, 누락·중복·순서·세대 교체를 어떻게 다루는가? | 상호작용·세션·이벤트 규칙 |
| 메시지·표현 | 어떤 정보를 어떤 타입·단위·선택성·버전으로 표현하는가? | 데이터 사전·메시지 후보·언어 간 대응 |
| RPC·전송 기술 | 요청/응답·stream·인증·deadline을 어떤 기술에 연결하는가? | gRPC/HTTP 등 매핑안 |
| 장비 binding | ROS action/topic·SDK·PLC 신호가 논리 계약을 어떻게 실현하는가? | 모델별 매핑·확인 가능/불가능 범위 |
| 저장·검증 | 어느 사실을 언제 남기고 재시작 때 무엇을 복원하는가? | 원자 기록 단위·시험 명세·추적표 |

예를 들어 gRPC는 호출과 stream을 제공하지만 RPC 종료·취소와 RX 작업의 물리 결과는 별도다. 한 stream의 순서 보존을 여러 연결·재연결 전체의 순서 보장으로 확대하지 않는다.[^1] 이러한 차이를 논리 계약에 먼저 적고 전송 기술을 연결한다.

## 4. 계약 경계 목록

아래 C 식별자는 설계 작업을 추적하기 위한 번호이며 API·네트워크 서비스의 최종 개수를 뜻하지 않는다.

| ID | 경계·주제 | 먼저 정할 책임·질문 |
|---|---|---|
| C01 | UI/운영자 ↔ platform | 작업지시·시작·중단·개입·조회, 사용자 권한과 중복 요청 |
| C02 | platform ↔ 공정 실행기 | run·단계 활성화·작업 요청·checkpoint·BT 재시작 |
| C03 | platform ↔ Device Adapter | 기능 조회·접수·실행·관측·결과·중단·재조정 |
| C04 | 관측·이벤트 ↔ 소비자 | 출처·품질·시간·순서·누락·재구독·snapshot의 의미 |
| C05 | 세션·제어권·수명주기 | 등록·준비·활성화·만료·세대 교체·정상 종료·소유자 |
| C06 | 패키지·모델 능력 ↔ 실행 허가 | 실제 적용 버전·필수 기능·교정·변경·미지원/미검증 |
| C07 | Runtime ↔ 저장 구현 | 의도·접수·결과·현재 상태·checkpoint의 기록·복원 |
| C08 | Adapter ↔ 실제 장비 | ROS/SDK/PLC 매핑과 근거. 제조사 원시 프로토콜을 새로 대체하지 않음 |

C04–C06은 C01–C03에 공통으로 적용될 수 있다. C07은 내부 저장 계약이며 반드시 네트워크 프로토콜로 만들지 않는다. 소스·레포 의존 방향과 실제 요청·관측의 양방향 흐름을 구별한다.

## 5. 설계 순서

| 단계 | 수행할 설계 | 핵심 산출물 | 다음 단계 조건 |
|---|---|---|---|
| 1. 경계·용어 정리 | C01–C08의 주체·소유 상태·사실과 판정 구분 | 책임 지도·용어표 | 같은 용어를 서로 다른 완료·허가 의미로 사용하지 않음 |
| 2. 대표 작업·사건 선정 | 유한 작업·목표 상태·모드 전환·스트림·수명주기 사례 선정 | 시나리오 카드 | 한 종류의 action에 모든 장비 기능을 억지로 맞추지 않음 |
| 3. 작업의 의미 계약 | 입력·접수·완료·실패·중단·개입·보장의 범위 | C03 첫 계약 카드와 대안 | 대표 사례를 실제 확보 가능한 근거로 설명 가능 |
| 4. 상태·식별·제어권·기록 | 누가 아는지, 상태가 왜 바뀌는지, 무엇을 저장하는지 추적 | 전이표·ID 관계·원자 기록·복구 규칙 | 정상·누락·중복·재시작·경합에 모순이 없음 |
| 5. 메시지 교환 규칙 | 세션·요청/응답·이벤트·재구독·취소·갭·흐름 제어 | RX 프로토콜 시퀀스·불가 동작 | 서로 기다리는 교착·무제한 대기·무조건 재전송이 없음 |
| 6. 데이터·전송 후보 | 타입·단위·존재성·오류·호환성을 정의하고 RPC/형식과 매핑 | 메시지 후보·Rust/C++ 대응·예제 값 | 표현 방식이 논리 의미를 잃지 않음 |
| 7. 교차 사례·호환 검토 | 다른 자사 모드·PLC·버전 조합으로 후보를 반박 | 반례·수정·호환 표·시험 벡터 명세 | 특정 모델에만 맞는 공통화가 드러나면 앞 단계 수정 |
| 8. 범위 있는 설계 기준판 | 첫 구현 대상 계약의 일관된 revision 정리 | 결정·제약·필수 후속 시험·구현 준비 항목 | 핵심 의미가 미결인 작업을 확정된 지원처럼 포함하지 않음 |

1–4를 먼저 한 묶음으로 검토한다. 5–8은 그 결과에 맞춰 진행하며 모든 항목을 한 번에 동결하지 않는다. 코드 실행을 통해서만 확인 가능한 사항은 후속 시험 의무로 남기고 문서 검토를 실제 시험 통과로 표시하지 않는다.

## 6. 대표 사례를 고르는 기준

| 사례군 | 설계 검토용 대상 | 드러낼 차이 |
|---|---|---|
| 조회·관측 | 장비 식별·상태·능력 | 연결됨·값 있음·현재 유효함의 차이 |
| 유한 작업 | OM-06 등의 JTC trajectory | 접수와 결과, goal과 operation의 연관성 |
| 목표 상태 요청 | 레이저 PLC의 문/척 작업 후보 | 이미 목표 상태인 경우와 새 동작 수행의 차이 |
| 모드 전환 | AS-02의 모드 선택 | 모드 활성화와 자세·이동 완료의 차이 |
| 장기 스트림 | FFW base 속도·leader teleop | 세션 허가·만료·명령 갱신, 유한 작업과의 차이 |
| 수명주기 | DHI 준비·종료 | 초기화·소멸도 물리 효과를 가질 수 있음 |

이는 설계 반례를 확보하기 위한 대표군이며 첫 투입 로봇·기계 순서를 확정하지 않는다. 자사 전체 기본 지원 의무는 유지하고, 대표군에서 얻은 공통 계약을 [13 지원표](13_robotis_support_matrix.md)의 모든 대상에 대조한다.

## 7. 계약 카드의 작성 형식

경계·작업 종류마다 아래 항목을 같은 형식으로 작성한다. 첫 버전은 문장·표 중심으로 만들고 실제 함수 선언은 뒤로 둔다.

| 항목 | 적을 내용 |
|---|---|
| 식별·범위 | 계약 ID/revision, 소비자·제공자, 포함/제외 책임 |
| 요구·근거 | 어떤 지원 ID·사용 사례·원문 사실에서 나왔는가 |
| 요청 의미 | 목표 상태인지 새 동작인지, 입력·단위·제어권·부작용 |
| 제공 보장 | 어떤 조건에서 무엇을 보장하며 무엇은 확인 불가인가 |
| 접수·진행·결과 | 각 사실의 생성자·판정자·보존·사용 조건 |
| 시간·자원 | 응답 기한·실행 감시·관측 신선도·세션 유효성, 공유 자원 |
| 중복·중단·복구 | 요청 동일성·유실·잔류 명령·재시작·개입 |
| 메시지·오류 후보 | 필요한 정보와 미지원·거부·불명·통신 오류의 구분 |
| 버전·검증 | 변경 영향·대체안·반례·예상 결과·추가 현장 확인 |

필수 관측이 없으면 그 부족을 표시하고 관측 보완·명시적 개입·실행 범위 제한을 검토한다. 필수 자사 지원 요구를 없애서 설계를 통과시키지 않는다. 장비 mapping이 미확정인 부분과 공통 의미 계약을 독립적으로 검토할 수 있는 부분을 구분한다.

## 8. 프로토콜 설계에서 놓치지 않을 질문

다음은 나중에 반드시 결정할 항목이지, 지금 선택된 메시지 필드는 아니다.

1. 요청·작업·run·단계 활성화·전달 시도·원본 장비 ID는 누가 생성하고 어디까지 유일한가?
2. 동일 요청과 다른 요청의 경계는 무엇이며, 기록을 얼마나 보존하고 보존 기간 이후에는 어떻게 응답하는가?
3. 접수 응답은 메모리 접수인가, 영속 기록인가, 장비 접수인가? 응답을 잃었을 때 무엇을 조회할 수 있는가?
4. 공정/장비 상태를 바꾸는 주체와 관측만 보고하는 주체의 권한은 어떻게 다르게 검증하는가?
5. 요청이 만료되는 시점과 실제 전달 직전의 제어권·프로파일 확인을 어떻게 연결하는가?
6. 이벤트 순서의 범위, 여러 stream 간 순서, 중복·갭·재구독·snapshot 뒤 따라잡기는 무엇을 보장하는가?
7. 보존해야 할 작업 사건과 최신값으로 합칠 수 있는 telemetry를 구별하고, 버퍼가 차면 어떻게 처리하는가?
8. 결과와 중단이 경합하거나 BT만 재시작하면 어느 기록·ID를 기준으로 복원하는가?
9. RPC deadline, 장비 실행 감시, 관측 유효성, 제어권/stream 만료의 시간을 어떻게 구분하는가?
10. 누락·0·false·미지원·미검증·invalid·unknown을 각 표현에서 구별할 수 있는가?
11. 입력의 단위·기본값·정규화·수치 한계·알 수 없는 필드를 어떻게 처리하는가?
12. 새/구버전·Rust/C++ 조합에서 메시지를 읽을 수 있다는 것과 같은 의미로 처리한다는 것을 어떻게 검증하는가?

Protobuf의 deterministic serialization은 보편적인 canonical 표현이 아니므로, 요청 의미의 동일성을 원시 직렬화 바이트 hash 하나로 정하지 않는다. 의미에 포함할 필드·기본값·단위·버전의 정규화 대안과 언어 간 예제 값을 먼저 검토한다.[^2] 필드 존재성과 기본값도 별도 설계 항목이다.[^3]

## 9. 검토와 확정 수준

| 문서 상태 | 의미 | 아직 주장할 수 없는 것 |
|---|---|---|
| 조사·초안 | 사실·질문·대안이 정리됨 | 선택 완료·호환성·동작 보장 |
| 사례 검토됨 | 지정 사건을 종이 위에서 추적하고 반례를 처리함 | 코드·실물 시험 통과 |
| 의미 기준안 | 범위·책임·상태·보존·복구의 제약과 선택이 기록됨 | 최종 wire/API 안정성 |
| 전송 후보안 | 의미를 보존하는 메시지·RPC·호환 대안이 있음 | 구현·성능·공개 장기 호환 보장 |
| 구현 준비 기준판 | 해당 첫 범위의 설계와 검증 의무를 맞춰 기록함 | 제품 출시·안전 적합·필수 현장 항목 해결 |

설계 기준판은 수정 불가능한 약속이 아니다. revision·변경 이유·영향 계약·재검토 사례를 남겨 변경한다. 해소되지 않은 핵심 의미·필수 관측 부족은 해당 작업의 준비 상태에 표시하고, 외부 공개·실행 지원 범위를 확대하지 않는다. 코드 구축은 별도의 후속 착수 단계다.

검토는 소비자 역할·제공자 역할·실장비/현장 역할·구현/지원 역할에서 같은 사건을 각각 설명해 보는 방식으로 한다. 실제 인원을 새로 가정하지 않으며 한 사람이 여러 역할을 맡을 수 있다.

## 10. 첫 검토 묶음과 후속 산출물

첫 묶음은 **C03 장비 작업의 의미 카드 1개 + C02/C04/C05/C07에 필요한 연결 + 정상/응답 유실/BT 재시작 사례**다. 단일 카드에서도 입력·접수·완료·불명의 의미가 일관되는지 확인한다. 이어서 모드 전환·스트림·driver 종료 사례로 공통화의 한계를 찾는다.

후속 상세 문서는 다음 주제로 작성한다. 아래는 계획 목록이며 모두 작성됐다는 뜻은 아니다.

- 계약 범위·용어·책임 및 상태 소유 지도.
- 유한 장비 작업·상태 전환·제어 세션별 의미 카드.
- 식별·세대·제어권·보존·재조정 명세.
- 관측·이벤트·시간·갭·snapshot 명세.
- 메시지·오류·버전·전송 매핑 후보와 Rust/C++ 대응.
- native binding·패키지/능력 연결·시험 명세·설계 기준판.

시작점과 미결 결정은 [작업·결정 목록](contracts/00_design_backlog.md), 실제 검토 방법은 [시나리오 검토집](contracts/01_scenario_workbook.md)에 준비했다.
