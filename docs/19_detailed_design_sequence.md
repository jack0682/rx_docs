# 계약 확정 이후의 상세 설계 순서

현재 상태: **초안 v0.1 마감**. 이 문서는 코드 착수 전의 설계 순서·선행 계획을 보존한다. 현재 구현/인계와 미결의 기준은 [초안 인계](implementation/draft_handoff.md)다.

2026-09-10 · 현재 작업: 설계 문서. 코드·실행 prototype·컨테이너 구축은 후속 착수 지시 이후다.

## 1. 출발점과 우선순위

[공통 작업 계약](contracts/v1.0/README.md)과 [셀 운영 계약](cell_operations/v1.0/README.md)을 구현 가능한 모듈·데이터·프로세스·납품 패키지로 구체화한다. 새로 제시할 순서는 아래 D1–D7이다. 기존 문서를 재사용하고 각 단계에서 필요한 검증 명세를 함께 작성한다.

**모듈·책임 → 실행·저장 → 장비/profile·공정 패키지 → 프로세스·배포 → 운영 화면 → 검증·인수 통합 → 종합 검토·구현 일감**

첫 셀의 실제 모델·신호·기구·개입 조건 확보는 이 순서와 병행한다. 그 값이 없다는 이유로 공통 모듈·저장·오류 처리 설계까지 중단하지 않는다. 반대로 빈 값을 임의로 채워 현장 실행 가능 상태로 승격하지 않는다.

## 2. 단계별 산출물

| 단계 | 구체화할 내용 | 산출물·완료 판단 | 선행 관계 |
|---|---|---|---|
| **D1 모듈 상세 구조** | 두 레포 안 모듈, 상태 소유자, 공개 API/내부 port, 허용 의존, 프로세스 경계 후보 | 모듈 책임표·의존도. 두 계약의 모든 주요 행위/기록을 담당 모듈에 배정 | 확정 계약·05/10 구조안 |
| **D2 실행·저장 공동 설계** | 명령 수용/평가/전달/관측의 실행 경로, 큐·우선순위·취소·동시성, DB schema·unique/CAS·transaction·outbox·Host journal·복원 | 정상 및 실패 지점별 시퀀스, 상태 소유/변경 규칙, 저장 schema·복원 설계. 계약의 원자성을 구현 구조로 설명 | D1. 실행과 저장은 함께 반복 검토 |
| **D3 profile·공정·현장 패키지** | artifact의 구체 schema, 장비 신호/작업 binding, 조건·기구/교정·소재 인계, recipe/activation/part 시도, 복구 plan, validator와 오류 | 장비 profile·현장 패키지 schema와 대표 작성본, 지원표 연결. 문서 사실/예시/미확정을 구별 | D1–D2 기준안과 현장 입력. D2와 병행 가능 |
| **D4 프로세스·두 이미지·릴리스** | supervisor와 시작/종료 순서, 무동작 software-ready, Host/ROS/BT/UI 배치, volume·권한·네트워크, CPU/GPU variant·의존 버전, manifest·업데이트·복원 | 14 이미지 명세를 확정 계약에 맞춰 상세화. 소프트웨어 재시작이 물리 활성/생산 재개가 되는 우회 경로가 없어야 함 | D2–D3의 상태/수명주기·의존 요구 |
| **D5 구성·운영·개입 화면** | 역할별 구성/검증/시작/대기/정지/복구/변경, 표시와 실제 허용 조건, API 오류/대기/재접속 | 화면 흐름·문구·API/상태 대응표. 왜 시작 불가인지와 필요한 다음 조치를 사용자가 알 수 있음 | 기본 흐름은 지금 초안 가능. 상세 확정은 D2–D4와 대조 |
| **D6 검증·인수 명세 통합** | 계약 적합성, 장애 주입, 혼합 버전, 자사 모델/variant, 장비·셀·설치/복원·운영 인수 | 기존 SC/CO/V/OV를 시험 ID·환경·입력·기대 결과·증거·담당·판정 근거에 연결. 설계 단계에서는 실행하지 않음 | 각 단계에서 누적 작성, D1–D5 이후 누락/중복 통합 |
| **D7 설계 기준판·구현 작업 분해** | 모듈/DB/profile/이미지/UI/시험 정합성, 남은 제약·의존, 첫 구현 범위·완료 조건 | 종합 설계판, 결정 기록, 의존 순서가 있는 구현 일감과 검증 연결. 이후 코드 착수 판단에 사용 | D1–D6의 선택 범위 검토 완료 |

레포 수·컨테이너 수·프로세스 수·모듈 수를 일치시키지 않는다. Rust 코어와 ROS/C++ 장비 스택의 경계, 자사 필수 지원, 두 계약의 의미는 입력으로 유지한다. 발견된 모순 때문에 계약 변경이 필요하면 영향/반례/호환을 기록한 별도 revision으로 다룬다.

## 3. 바로 다음 작업: D1 모듈 상세 구조

다음 회차에서 작성할 것은 **‘모듈별 책임·상태 소유·의존 관계 명세’**다. 디렉토리 이름부터 고정하기보다 다음 행을 채운다.

| 모듈별 필드 | 결정할 것 |
|---|---|
| 목적과 경계 | 어떤 계약 책임을 구현하고 어떤 다른 모듈과 연결하는가 |
| 소유 상태 | run·operation·cell/scope·mandate·permit·case·budget 등의 최종 writer |
| 입력·출력 | 사용하는 공통 타입·명령·사건·내부 port 및 호출 주체 |
| 실행/동시성 | 동기/비동기 처리 위치, 직렬화 단위, 외부 I/O·제어 loop와의 관계 |
| 저장/실패 | transaction 참가, durable/volatile 구별, 기동·중단·오류 때의 책임 |
| 의존·배포 | 어느 레포·프로세스/라이브러리에 두고 무엇을 참조할 수 있는가 |
| 검증 연결 | 책임을 확인할 SC/CO/OV와 후속 시험 |

분해 대상은 platform의 도메인 판단·application 조정·운영 API·저장 adapter·조건/허가/복구 서비스와, solutions의 Host·native adapter·BT/recipe 실행·profile/site package·UI·supervisor다. 이는 검토할 책임 목록이며 각각 별도 프로세스나 별도 crate로 만들겠다는 확정이 아니다.

D1에서는 최소 네 흐름을 같은 책임표에 대입한다: **정상 operation, 응답 유실, 사람 개입 후 재시작, 소프트웨어 시작/종료**. state writer가 중복되거나 어느 모듈도 책임지지 않는 단계가 있으면 다음 상세화 전에 고친다.

## 4. 병행할 현장 입력

| 입력 | 영향을 받는 설계 | 현재 없이 진행 가능한 것 |
|---|---|---|
| 첫 로봇·그리퍼·지그·소재 조합 | 실제 profile·교정/지지·기동/정지 조건·지원 variant | 모듈 경계·타입/schema·저장/오류 처리 구조 |
| 실제 작업 순서·‘빼기’의 의미·병행 범위 | recipe와 part/activation mapping | recipe 모델과 validator 설계. 순서 예시는 가정 표시 |
| PLC/레이저/OEM 신호와 기능 | native binding·진입/가공/정지·관측·검증 | adapter 책임·미지원/미확인 처리·기록 규칙 |
| 작업자 개입·접근·복귀 절차 | 실제 case/recovery plan·UI·현장 인수 | case schema·상태/권한·원자성·표시 흐름 |
| 안전기능/환경/시간 검증 근거 | Qualification·commissioning·실물 시험 판정 | 근거 연결·허용 범위·검증 의무의 데이터 설계 |

현장 입력은 확인한 값과 출처를 추가하는 작업이다. 소프트웨어 계약이 필요한 값을 결정해주는 것은 아니다. 실제 값이 필요한 실행/안전 성능 판단은 계속 미확정으로 표시한다.

## 5. 각 단계에서 검증 명세를 함께 작성한다

D1에서 모듈 책임과 계약 사례를 연결하고, D2에서는 각 commit/전달 경계의 고장을, D3에서는 schema·장비 차이를, D4에서는 재기동/복원을, D5에서는 작업자 오해·중복 요청·재접속을 명세한다. D6는 이 결과를 모아 시험 범위와 증거를 정리하는 단계다.

현재의 문서 검토, 후속 소프트웨어 시험, 실제 장비/셀 검증, 기능안전 검증은 별개다. 첫 소프트웨어 구현 범위를 정리할 수 있다는 사실을 첫 현장 운전 허가와 혼동하지 않는다. 자사 한 모델의 사례를 먼저 상세화하더라도 전체 기본 지원 의무는 [13 지원표](13_robotis_support_matrix.md)에 유지한다.

## 6. 코드로 넘어갈 때 필요한 결과

- 선택한 첫 구현 범위의 모듈·타입·내부 port·상태 소유자가 정해져 있다.
- 각 명령의 transaction·native 진입·복구 경로가 두 계약과 일치한다.
- 배포 조합·기동/종료·설정/자료 schema와 필요한 검증을 설명할 수 있다.
- 미확정 현장 조건과 구현 가능한 소프트웨어 범위를 구분한 일감이 있다.
- 후속 코드 착수 지시를 받은 뒤 구현·빌드·시험을 진행한다.

이 계획은 기존 S1–S8의 전체 로드맵 중 상세 구조·현장 패키지·구현 준비를 진행할 순서다. 첫 코드를 시작하기 전에 모든 미래 장비의 상세 설계/실물 인증을 끝내야 한다는 뜻은 아니다. 특정 납품·지원 선언에 필요한 조건은 해당 범위에서 충족해야 한다.
