# 06. 공통 계약·데이터·신뢰성

> 2026-09-10 현재 계약의 규범 기준은 [RX 계약·프로토콜 v1.0](contracts/v1.0/README.md)이다. 이 문서의 선행 제안·예시는 v1.0과 충돌하면 대체된다. 자사 기본 지원 의무·두 이미지 경계는 유지하며, 실제 구현·실물 검증은 별도다.

현재 작업 단계: **설계 문서 작성·구체화**. 실제 코드·빌드 기반·저장소 구축은 설계 정리 후 후속 지시에 따라 진행한다. 진행 순서는 [설계 로드맵](/Users/ojaehong/RX_automation/rx_ws/docs/00_design_roadmap.md)을 따른다.

[전체 문서 안내](/Users/ojaehong/RX_automation/rx_ws/README.md) · 상세 출발점: [첫 셀 계약 v0.2](/Users/ojaehong/RX_automation/rx_ws/docs/11_first_cell_contract.md)

이 장의 개념·상태·필드는 설계 입력이다. 후속 [계약·프로토콜 설계 계획](15_contract_protocol_design_plan.md)의 사례·대안 검토를 거쳐 의미·표현·전송을 구체화하며, 지금 공개 API나 wire 규약으로 동결하지 않는다. 이 장에서 코어와 외부 경계를 함께 설명한 부분은 platform 실행 서비스의 책임이며 순수 Core가 외부 I/O를 직접 수행한다는 뜻은 아니다.

## 1. 인터페이스보다 먼저 정할 의미

공통 인터페이스는 함수 이름과 파라미터 목록만으로 완성되지 않는다. 작업 책임, 시작 조건, 요청 동일성, 접수, 완료 근거, 중단, 시간 초과, 재시작을 설명할 수 있어야 한다. 실제 작업 하나의 정상·거부·응답 유실 사례에서 이 의미를 정하고 타입·API로 표현한다.

공통으로 만드는 것은 모든 장비의 기능 집합이 아니라 요청·관측·결론을 다루는 규칙이다. 장비가 제공하지 않는 완료·중단 근거는 스키마만으로 만들어낼 수 없다.

## 2. 제품 데이터의 관계

| 객체 | 의미 | 연결할 정보 |
|---|---|---|
| 현장·셀 | 함께 운영할 장비·자원의 논리적 구성 | 설치 위치, 책임, 활성 패키지 |
| 장비·자원 | 기능 제공 대상과 배타 사용·조정 대상 | 장비 ID, 공유 공간·척·로봇 사용 조건 |
| 어댑터·프로파일 | 통신 구현과 실제 기계에 적용하는 의미 | SDK·firmware·설정·신호·검증 버전 |
| 공정 정의 | 작업 순서·조건·복구의 버전 있는 정의 | 필요한 능력·품목·tool·지그 참조 |
| 작업지시 | 무엇을 어떤 조건으로 얼마나 처리할지 | 품목·수량·공정 버전·우선순위 |
| 공정 실행 | 지시를 실제 수행하는 한 실행 | 적용 패키지, 단계, 장비 작업·개입 |
| 장비 작업 | 특정 장비에 요청한 논리적 작업 | operation ID, 입력, 접수·관측·결론 |
| 전달 시도 | 장비에 요청을 전달하려 한 개별 시도 | attempt ID, 연결 세대·원본 요청 ID |
| 관측·결과 | 장비가 제공한 사실과 판정 | 출처·품질·시각·요청 연관성·원본 코드 |
| 소재·품질 기록 | 실제 식별·검사 범위의 소재 정보 | lot/개체 식별 방식, 보유·이동·검사 근거 |
| 개입·배포 기록 | 사람의 조치와 사용 버전의 이력 | 주체·시각·이유·확인 범위 |

작업지시 하나에서 여러 공정 실행과 장비 작업이 생길 수 있다. 취급 완료, 가공 완료, 검사 합격, 작업지시 완료는 각각 별도 조건이다. 첫 셀에 검사 장치나 개체 식별 수단이 없다면 그 능력을 구현 완료로 표시하지 않는다.

## 3. 경계별 계약

| 경계 | 최소 요청·조회 | 필수 규칙 |
|---|---|---|
| 앱 → RX | 구성·공정·작업지시 조회, 시작·중단·개입 요청 | 주체·권한·대상·버전·중복 요청 |
| 공정 실행기 → 코어 | 작업 시작·상태·중단, 자원 요청 | 반복 호출의 동일성, 순서·경합 |
| 코어 → 장비 모듈 | 능력 조회, 작업 전달, 관측·결과, 지원 중단·재조정 | 접수와 완료 구분, 미지원·불명 표현 |
| 코어 → 저장·기반 구현 | 원자적 기록 단위, 조회·시간·이벤트 전달 | 실패·재시작·순서·일관성 |
| 공정관리 → 실행/실적 | 지시와 배정, 진행·완료 근거 | 중복 집계·재작업·보류·취소 처리 |

능력은 장비 전체가 아닌 작업별로 선언한다. `supported / unsupported / unverified`를 구별하고, 완료 관측·요청 연관·중단·재접속 조회·장비 측 중복 억제의 수준을 적는다. 버전 있는 작업별 입력·결과 스키마를 제공한다.

공정은 각 작업에 필요한 최소 관측·결과·중단 근거를 선언하고, 적용 프로파일의 능력과 대조한다. 근거가 부족하면 해당 자동 실행 범위를 제한한다. 작업자 확인을 포함한 다른 절차로 바꾸거나 장비·센서·PLC 논리를 보완할 수 있으며, 선택한 방식의 비용·개입·검증을 공정 패키지와 인수 범위에 반영한다. 사람 확인은 확인할 수 있는 범위에만 사용하고 필수 보호 기능을 대신하지 않는다.

## 4. 요청과 결과의 식별

`operation_id`는 하나의 논리 작업을, `attempt_id`는 전달 시도를, `native_request_id`는 장비가 제공하는 요청 식별자를 뜻한다. 같은 operation ID의 동일 의미 요청은 기존 작업 상태를 반환하고, 같은 ID의 다른 대상·입력·적용 버전은 거부한다.

요청 내용의 digest를 사용한다면 단위·기본값·수치 표현·정규화 규칙도 정의해야 한다. 전송 frame의 순번을 작업 식별자로 대신하지 않는다. 장비의 순환 번호·재부팅 후 번호 재사용도 프로파일에서 다룬다.

작업의 의미가 ‘목표 상태 충족’인지 ‘새 동작 수행’인지도 중요하다. 이미 문이 닫혀 있을 때 현재 상태 확인으로 완료할 수 있는 요청과, 새로운 동작 사이클을 요구하는 요청은 동일하지 않다.

## 5. 접수·활동·결론

RX가 요청을 저장한 것, 장비가 수락한 것, 장비가 움직이는 것, 작업이 완료된 것을 구별한다. 활동 상태와 결론은 별도 차원으로 관리한다.

| 결론 | 의미 |
|---|---|
| pending | 선언된 대기·관측 범위 안에 있고 결론을 기다림 |
| succeeded | 이번 요청에 연결된 필수 완료 조건이 입증됨 |
| failed | 정의된 실패 조건이 입증됨. 부분 동작은 별도 보존 |
| rejected | 실행 대상으로 접수되지 않았음이 확인됨 |
| cancelled | 정의된 취소·중단 범위가 확인됨. 초기 물리 상태를 뜻하지 않음 |
| unknown | 현재 증거로 이번 작업의 결론을 확정할 수 없음 |

장비 활동은 idle·executing·paused·정지 관측·불명 등으로 표현한다. 현재 idle이어도 이전 작업이 성공했는지는 모를 수 있다. 현재 실행 중이어도 정확히 어느 요청인지 연관하지 못하면 해당 작업의 결론 불명은 해소되지 않는다.

## 6. 대표 전이와 경합 규칙

| 사건 | 처리 원칙 | 금지할 해석 |
|---|---|---|
| 전달 전 거부가 입증됨 | rejected와 사유 기록 | 단순 timeout을 미실행으로 취급 |
| 장비 접수·진행이 확인됨 | 근거를 기록하고 pending 유지 | 접수 즉시 succeeded |
| 해당 요청의 완료 근거 확보 | succeeded와 근거 연결 | 다른 작업의 완료 bit 재사용 |
| 필수 관측 유실·판정 불가 | unknown, 의존 후속 작업 제한 | 폴링 횟수로 결론 생성 |
| 중단 요청만 수락됨 | 중단 대기와 별도 상태 확인 | 곧바로 cancelled·자원 해제 |
| 늦은 완료와 중단 결과 경합 | 요청 연관성과 장비별 판정 규칙으로 조정 | 메시지 도착 순서만으로 승자 결정 |
| 확정된 결과 뒤 중복 통지 | 동일 기록과 대조·중복 처리 | 실적 중복 증가 |
| 확정된 결과와 충돌하는 새 근거 | 충돌 사건·재조정 기록, 필요 시 후속 제한 | 과거 근거를 지우고 조용히 덮어쓰기 |

첫 구현에서는 선택한 작업의 구체적인 상태 전이표와 경합 시험을 작성한다. 이 표는 전체 시스템의 모든 전이를 완성한 형식 명세가 아니다.

## 7. 관측의 유효성과 출처

관측에는 원본 장비·신호, 값·단위·좌표계, 품질, RX 수신 시각, 원본 시각의 의미, 연결 세대·원본 순번, 작업 연관 근거, 프로파일 버전을 포함한다. 원본이 제공하지 않는 시각이나 confidence는 임의로 채우지 않는다.

주기 스트림에서는 갱신 지연·누락을 확인한다. 변경 때만 통지하는 신호는 연결·품질·heartbeat 의미를 함께 확인한다. 값이 오래 바뀌지 않았다는 사실과, 장비에서 새 상태를 확인하지 못했다는 사실은 다르다.

구체적인 제조사 사례는 [인터페이스 연구보고서](/Users/ojaehong/research_RX/RX_first_cell_interface_research_v1.0.md)에 있다. 이 기준서에서는 제조사 반환값을 바로 공정 완료로 해석하지 않는 규칙을 공통으로 적용한다.

## 8. 저장과 물리 동작의 경계

설계 시작안은 작업 현재 상태, 판정 이벤트, 적용 구성·버전을 함께 저장하는 방식이다. 같은 논리 상태 변경에 해당하는 기록은 하나의 저장 트랜잭션으로 처리한다. 조회용 집계가 별도로 있다면 원본 상태와의 관계·갱신 지연을 명시한다.

장비 전달 전에 필요한 의도 기록을 내구성 있게 남기고, 전달·접수·결과를 이후 기록한다. 저장소가 쓰기를 확정하지 못하면 해당 신규 작업 전달을 허가하지 않는 정책을 기본으로 검토한다. 이미 진행 중인 장비와의 단절·정지 책임은 장비별로 정의한다.

**데이터베이스 기록과 장비의 물리 실행은 하나의 원자적 트랜잭션이 아니다.** 장비 실행 직후 PC가 중단되면 결론이 불명일 수 있다. 장비 측 요청 식별·중복 억제·결과 보존 없이 exactly-once를 약속하지 않는다. 전송 대기열을 영속화하더라도 재시작 때 모든 항목을 자동 재전송하지 않는다.

## 9. 재시작·제어권·자원

재시작 시 저장된 미결 작업을 불러오고, 장비·프로파일·모드·제어권·현재 상태를 다시 확인한다. 이전 명령의 큐 잔류와 지연 실행 가능성을 처리한 뒤 관련 자원과 후속 동작을 허가한다. 현재 정지 상태만으로 명령이 남아 있지 않다고 판단하지 않는다.

RX 내부 자원 lock만으로 펜던트·외부 PLC·다른 PC의 명령까지 차단되는 것은 아니다. 장비에서 제어권을 보장하는 수단과 운영 절차를 확인하고 그 범위에 맞게 선언한다. 리소스는 작업의 terminal 결과가 생겼다는 이유만으로 자동 해제하지 않는다.

## 10. 설정·권한·기록 보존

실행은 적용한 공정·장비·tool·교정·정책 버전을 고정 참조한다. 구성 변경과 데이터 스키마 변경은 호환성·재검증 대상으로 관리한다. 계정 비밀을 공정 패키지나 로그에 저장하지 않고 필요한 저장 위치를 참조한다.

모든 화면의 직접 장비 쓰기를 차단하고 Runtime의 권한·감사 경로를 사용한다. 원격 지원도 별도 권한·현장 운영 조건·기록에 따라 수행한다. 저장 용량 부족, 시계 변경, 오래된 캐시, 모듈 crash를 명시적인 운영 사건으로 다룬다.

일반 명령 API와 작업자 확인 기능을 안전 보호 장치로 승격하지 않는다. 안전 기능과 일반 자동화 제어의 책임·검증은 납품 설계에서 별도로 정한다.
