# 계약·프로토콜 시나리오 검토집 v0.1

> 선행 계획/사례 준비 기록이다. 현재 작업 결과는 [v1.0 기준판](v1.0/README.md), [결정 종료](v1.0/05_decisions.md), [실제 문서 trace 검토](v1.0/06_scenarios_and_validation.md)를 따른다. 아래의 미완료·미결 표현은 이 계획을 작성한 당시 상태다.

[설계 계획](../15_contract_protocol_design_plan.md) · [결정 목록](00_design_backlog.md)

이 검토집은 문서 위에서 후보 계약을 검토하기 위한 사건 집합이다. 정상·고장을 실제 장비에 실행하는 절차가 아니다. 지원 ID는 [자사 기본 지원표](../13_robotis_support_matrix.md)를 따른다.

## 1. 공통 검토 방법

각 사례마다 주체를 UI·platform·BT·Adapter·장비·저장·작업자로 나누고 사건을 한 단계씩 추적한다. 모든 주체가 같은 시점에 같은 사실을 안다고 가정하지 않는다. 결론이 필요한데 근거가 없으면 누가 무엇을 추가 확인해야 하는지 적는다.

| 기록할 항목 | 내용 |
|---|---|
| 시작 조건 | 실제로 확인된 것, 설계상 가정, 미확정 항목 |
| 사건 | 요청·전달·접수·관측·중단·연결 변화·사람 조치 |
| 주체별 지식 | 보낸 사실·받은 사실·현재 알 수 없는 것 |
| 기록 | 영속된 것·메모리만 있는 것·저장 여부 불명 |
| 판단·후속 | 후보 계약에서 가능한 결론, 허용·보류할 일 |
| 반례·결정 | 대안이 깨지는 이유, 관련 D 번호와 수정점 |

레이저 PLC의 문/척 작업은 실제 신호가 미확정이므로 목표 상태 요청의 추가 비교 카드로 사용한다. 첫 실물 동작을 정한 것으로 간주하지 않는다. SC01의 유한 작업 결과를 모든 다른 유형에 그대로 적용하지 않는다.

### SC03의 재시작 변형

| 변형 | 살아 있는 주체 / 재시작한 주체 | 추가 질문 |
|---|---|---|
| SC03-A | Host·장비는 유지 / platform 재시작 | 영속 작업과 이전 Host 대기·전송을 어떻게 조정하는가? |
| SC03-B | platform·장비는 유지 / Host 재시작 | Host 메모리 접수 기록이 없을 때 미실행으로 오인하지 않는가? |
| SC03-C | platform·Adapter는 유지 / 장비·PLC 또는 ROS controller만 재시작 | 이전 관측·결과·모드·제어권이 여전히 유효한가? 장비 쪽 작업 이력 유실을 어떻게 표현하는가? |

SC03-C에서는 재시작을 식별할 장비 근거가 있는지, 없다면 어떤 한계를 선언할지부터 검토한다. 재개 전에 버전·모드·제어권·관측·잔류 명령·현재 물리 상태 중 무엇을 다시 확인할지 적는다. 이전에 영속된 완료 사실을 장비 재시작 때문에 지우는 것과, 그 완료 당시의 물리 상태를 현재에도 유효하다고 간주하는 것은 서로 다른 문제다.

## 3. SC02의 첫 사건 카드 — 방법 예시

아래는 첫 논의를 시작하기 위한 가상 사건이다. 프로토콜·상태 이름의 최종 선택은 아니다.

| 단계 | 일어난 사건 | platform이 아는 것 | Adapter/장비 쪽 상황 | 남은 설계 질문 |
|---|---|---|---|---|
| A | UI/BT가 작업을 요청 | 요청 내용 도착 | 아직 이번 요청 없음 | 누가 ID·중복 키를 제공하는가? |
| B | platform이 의도를 기록한 뒤 전달을 시도 | 의도 기록과 전송 시도 | 수신 여부는 platform에 미확인 | 전송 전·후 기록의 최소 단위는? |
| C | Adapter가 요청을 받고 장비에 전달했지만 응답 경로가 끊김 | 접수/결과를 확정할 수 없음 | 장비는 실행했을 수도, 접수하지 않았을 수도 있음 | timeout을 어떤 오류·결론으로 표현하는가? |
| D | 같은 요청을 호출자가 다시 제시 | 과거 전송 이력 존재 | 이전 작업 결과 보존 능력은 모델별 차이 | 같은 작업을 조회하는가, 어떤 경우에 재요청을 허용하는가? |
| E | 연결 복구 후 장비가 idle로 관측됨 | 현재 idle 관측 | 이전 성공·중단·미실행은 아직 구분 안 될 수 있음 | 어떤 추가 증거가 있어야 결론을 낼 수 있는가? |

처음 비교할 대안은 ‘timeout이면 실패로 끝냄’과 ‘결론 불명으로 보존해 재조정함’이다. 전자는 실제로 수행된 명령의 재실행을 유발할 수 있는 사례에서 반박해야 한다. 후자는 어떤 정보를 보존하고 어느 후속 작업을 제한할지까지 설명해야 한다. UNKNOWN이라는 단어를 추가하는 것만으로 설계를 완료하지 않는다.

검토자는 요청 식별·접수 내구성·실제 결과 조회 능력이 없는 장비에서도 후보 계약이 정직하게 자신의 한계를 표현하는지 확인한다. 불명 상태가 장비 정지를 뜻하지 않는다는 점과, 미결 작업 관련 자원을 언제 해제할 수 있는지를 별도로 적는다.

## 4. 대안 비교에 사용할 입력 예시

정규화·호환 설계에서는 다음 쌍을 같은 요청으로 볼지, 다른 요청으로 볼지, 잘못된 입력으로 거부할지를 이유와 함께 적는다. 실제 canonical 형식·hash 알고리즘·필드 번호는 아직 정하지 않는다.

- 선택 필드 누락 / 명시적인 0·false·빈 문자열.
- 같은 물리량의 서로 다른 허용 단위 표현 / 허용되지 않은 단위.
- 입력 map 순서만 다른 요청 / 순서가 의미를 갖는 관절 배열 변경.
- 같은 operation ID와 같은 내용 / 같은 ID와 다른 tool·교정·프로파일.
- 알려진 enum / 새로운 enum 또는 필수 능력 버전.
- 정상 수치 / NaN·무한대·범위 밖 값.
- 같은 의미의 메시지 / 다른 직렬화·라이브러리 버전의 바이트.

결과는 언어 간 시험 벡터 명세로 남겨 나중에 Rust·C++ 구현이 같은 판단을 하는지 확인할 입력으로 사용한다. 현재 실행 비교나 serializer 테스트는 수행하지 않는다.

## 5. 회차 종료 시 남길 것

검토한 계약·사례·revision, 주체별 사건표, 발견한 모순·반례, 대안의 장단점, 채택/미결 결정, 추가로 필요한 장비 사실, 영향을 받는 지원 ID·이미지 요구를 남긴다. 필수 시나리오를 설명하지 못한 상태에서 API 이름이나 전송 기술의 편의만으로 계약을 동결하지 않는다.

현재 상태는 **사례 준비 및 예시 카드 작성**이다. 전체 사례의 walkthrough·합의·구현·실물 검증을 완료한 상태는 아니다.
