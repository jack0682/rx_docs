# RX 설계 로드맵

현재 상태: **초안 v0.1 마감**. 이 문서는 코드 착수 전의 설계 순서·선행 계획을 보존한다. 현재 구현/인계와 미결의 기준은 [초안 인계](implementation/draft_handoff.md)다.

## 1. 현재 작업 방식

**설계 문서를 먼저 작성하고 단계적으로 구체화한 다음, 코드 구축에 착수한다.** 기존의 작은 코드를 일찍 만들어 검증하는 계획은 후속 구현 단계로 옮긴다. 현재 할 일은 문서·도식·사례·표를 통해 모순과 미결 사항을 줄이는 것이다.

설계 범위는 우선 첫 레이저 셀과 재사용할 공통 제품의 경계다. 장기 확장 대상 전체의 상세 설계를 끝내야만 첫 제품 코드를 시작할 수 있다는 뜻은 아니다. 첫 구축 범위가 구현 가능한 수준으로 정리됐을 때 후속 코드 착수를 논의한다.

## 2. 설계 순서와 산출물

| 단계 | 구체화할 것 | 남길 설계 문서 | 완료 판단 |
|---|---|---|---|
| S1 제품·첫 범위 | 목적·납품 범위·첫 셀·장비·품목·사이클 | 제품 정의, 범위표, 사실·미결 목록 | 만들 제품과 첫 적용 범위를 설명 가능 |
| S2 사용 흐름·책임 | 구성·검증·운영·개입, 로봇·PLC·작업자 책임 | 사용 사례, 책임표, 정상·이상 흐름 | 누가 무엇을 결정·확인하는지 명확 |
| S3 논리 구조·레포 | 앱·공정관리·실행기·코어·장비 모듈·저장 | 구성도, 모듈 명세, 의존성·레포 배치 | 공통 부분과 현장 부분의 경계가 설명됨 |
| S4 데이터·공통 계약 | 장비·작업·관측·결과·구성 버전과 인터페이스 | 객체 관계, 스키마·요청/응답 예시 | 첫 작업을 끝까지 같은 의미로 표현 가능 |
| S5 상태·복구·제어권 | 접수·완료·불명·중복·중단·재시작·잔류 명령 | 전이표, 시퀀스도, 경합·복구 사례 | 정상뿐 아니라 불확실한 경우도 판단 가능 |
| S6 현장 패키지·운영 | 프로파일·공정·tool·교정·배포·권한·지원 | 패키지 명세, 화면 흐름, 설치·복원·지원 설계 | 현장별 차이와 운영 책임이 연결됨 |
| S7 검증·구현 준비 | 계약·모의·실물·인수의 시험과 구현 의존성 | 시험 명세, 단계별 판정표, 구현 작업 분해 | 나중에 무엇을 만들고 어떻게 확인할지 명확 |
| S8 설계 종합 검토 | 문서 간 모순·추정·미결·범위와 기술 선택 | 설계 기준판, 결정 기록, 남은 제약 | 선택한 첫 구축 범위의 코드 착수 판단 가능 |

문서 검토 중 새 사실이나 모순이 드러나면 앞 단계로 돌아가 수정한다. S8까지의 산출물은 설계 문서이며 실행 가능한 제품·프로토타입을 만들지 않는다. 장비·제조사 자료의 읽기와 조사는 설계를 위한 근거 수집으로 진행할 수 있다.

## 3. 첫 구체화 대상

현재 Rust·두 컨테이너 경계를 바탕으로 [계약·프로토콜 v1.0 기준판](contracts/v1.0/README.md)을 작성하고 반례/독자 검토를 수행했다. S4·S5의 공통 계약 선택은 [결정 기록](contracts/v1.0/05_decisions.md)에 정리됐다. [15 설계 계획](15_contract_protocol_design_plan.md)은 선행 계획으로 보존한다. 다음은 v1.0의 검증 의무와 현장별 미확정 binding·공정·운영 화면·납품 조건을 상세화하는 단계다. S6–S8 전체 및 실물 지원 완료를 뜻하지 않는다.

이번 기준판에서 답한 질문은 다음과 같다.

1. 각 계약의 소비자·제공자·상태 소유자와 제공 보장의 범위는 무엇인가?
2. 유한 작업·상태 전환·제어 세션·수명주기를 어떤 공통 의미와 작업별 의미로 나누는가?
3. 정상·유실·중복·재시작·경합에서 누가 무엇을 알고 어떤 기록이 필요한가?
4. 그 의미를 데이터·메시지·전송 기술에 어떻게 손실 없이 연결하는가?
5. 어떤 대안·반례·검토 기준을 통과한 범위를 설계 기준판으로 정리할 것인가?

이 목록은 설계 작업 항목이며 지금 답변이나 파일 제공을 추가로 요구하는 질문 목록은 아니다.

안전·위험성평가 자료를 연결한 [16 후속 설계 입력](16_safety_requirements_contract_link.md)에 따라, 첫 셀의 개입·정지/지지·변경 후 재검토 사례를 S4–S7에 연결한다. v1.0 공통 계약의 확정과 현장 안전기능 명세의 완성을 구별한다.

[17 다음 설계 분석](17_cell_operation_design_analysis.md)은 후속 구체화 단위를 셀 운영 계약으로 제안한다. 첫 작업은 N01 사용 조건·셀 경계와 N02 부분 사이클의 작업자 개입·복구 카드이며, N03–N06에서 기능 할당·허가/무효화·UI/binding·반례를 연결한다. 이 개념 제안은 새로운 프로토콜 기준판이나 실물 운전 허가가 아니다.

N01–N06의 규범적 결과는 [18 셀 운영 계약 v1.0](18_cell_operations_contract.md)에 정리됐다. 운전 조건·허가·개입·복구·변경·base 계약 연결과 반례를 확정했고, 실제 신호/장비/현장 조건 및 OV01–OV11은 commissioning/구현 검증 의무로 남는다.

현재 다음 설계 작업은 [19 상세 설계 순서](19_detailed_design_sequence.md)의 D1 모듈별 책임·상태 소유·의존 관계 명세다. D2 실행/저장부터 D7 구현 준비까지 연결하며, 현장 입력 확보와 각 단계의 시험 명세는 병행한다. 실제 코드 구축·실물 운전의 완료/착수 선언은 아니다.

## 4. 두 레포의 설계 전제

| 향후 레포 | 책임 |
|---|---|
| `rx-platform` | ROS 비의존 공통 계약·코어·Runtime·운영 API·기록·복구·계약 시험·코어 컨테이너 |
| `rx-solutions` | ROS 2·자사 필수 패키지 전체·전이 의존성·장비 어댑터·BT·구성/운영 UI·현장 패키지·납품/검증·솔루션 컨테이너 |

솔루션이 특정 플랫폼 버전을 사용하고 플랫폼은 특정 고객·현장을 참조하지 않는 방향으로 설계한다. 실제 디렉토리·레포 초기화와 빌드 연결은 후속 코드 구축 단계에서 진행한다.

RX 두 레포의 컨테이너와 자사 패키지 기본 지원을 먼저 설계한다. Rust 코어 선택의 근거와 C++/ROS 연동의 세부 스택안은 [스택·컨테이너 제안](12_stack_and_container_proposal.md)에 있다. 컨테이너 수와 내부 제어 프로세스 수는 구별한다.

## 5. 설계와 구현의 구분

현재 작성할 수 있는 것은 API·데이터·상태의 명세와 예시, 도식, 의사코드, 시험 시나리오, 결정·미결 기록이다. 제품 소스·실행 프로토타입·빌드 환경·CI·패키지 배포·장비 연결 코드는 아직 구축하지 않는다.

설계 검토를 마치면 [후속 구현·검증 계획](07_future_implementation_and_validation.md)을 다시 맞춰 코드 착수 순서를 정한다. 구현에서 새 사실이 드러날 가능성은 설계의 가정·검증 항목으로 남기되, 이를 이유로 현재의 문서 우선 순서를 건너뛰지 않는다.

## 6. 문서 관리

각 설계 항목에 요구·관측 사실·제안·미결의 상태와 근거를 남긴다. 문서 간 이름과 책임이 바뀌면 관련 다이어그램·계약·검증 항목을 함께 갱신한다. 기존 리서치 원본은 보존하고 이 작업 공간의 설계를 최신 작업본으로 관리한다.
