W01–02에서 확인한 사실을 바탕으로 W03부터 작은 범위를 반복 검토한다. W06의 전송 형태가 선행 작업의 의미를 임의로 바꾸면 W03–05로 돌아간다. 코드·컨테이너·실물 시험은 현재 작업 목록에 포함하지 않는다.

W06 착수 전에는 작업 종류·책임·요청 동일성의 의미·접수/결과·권한·기록·기본 복구 조건을 기준안으로 정리한다. D01–10의 모든 세부사항이 끝나야 하는 것은 아니다. D07의 의미에 포함할 정보는 먼저 검토하되 정규화 표현·hash 상세는 W06–07에서, D10의 권한·필수 능력 판정 의미는 먼저 정하되 wire 응답·버전/enum 표현은 W06–07에서 구체화한다. 후속 결과로 의미를 수정하는 피드백과, 후속 산출물을 미리 요구하는 착수 조건을 구분한다.

## 3. 결정 기록에 남길 것

결정마다 문제, 범위, 사실/가정, 최소 두 대안, 비교 사례, 선택 이유, 제공 보장과 한계, 영향 계약·지원 ID·이미지 요구, 검토 주체·revision, 미해결 검증 항목을 기록한다. 단순히 “더 깔끔하다”거나 “라이브러리가 기본으로 그렇게 한다”는 이유만으로 선택하지 않는다.

중요 대안이 사실상 하나뿐이면 배제 사유와 외부 제약을 적는다. 장비 프로토콜의 고정된 기능과 RX에서 자유롭게 선택할 수 있는 의미·표현을 구별한다.

## 4. 현장 정보가 부족할 때

- 코어·공통 계약에 필요한 일반 의미는 사례와 가정을 명시해 검토한다.
- 실제 native API·신호·동작 조건이 확인되지 않은 부분은 해당 binding 카드에 남긴다.
- 완료·중단·제어권의 필수 근거가 부족한 작업은 보완·개입·제약을 결정하기 전까지 구현 준비·지원 완료로 표시하지 않는다.
- 자사 필수 지원 항목은 미결 작업으로 유지한다. 자료 부족을 이유로 필수 요구를 선택 기능으로 바꾸지 않는다.

## 5. 첫 검토 회차의 완료 기준

첫 회차의 결과는 최종 계약이 아니다. W01–03의 초안과 SC01·02·05의 사건 추적, 새로 드러난 D01·03·08 등의 대안·반례를 얻으면 된다. 다른 작업 유형을 검토하기 전에 해당 세 사례에서 누가 무엇을 아는지·어떤 기록이 필요한지 일치하는지 확인한다.

현재 이 문서는 작업·결정 항목을 준비한 상태다. W01–08을 수행 완료한 것으로 표시하지 않는다.
